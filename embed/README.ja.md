# eg2e — EmbeddingGemma 2 のベクトル化と類似検索

[`google/embeddinggemma-2`](https://huggingface.co/google/embeddinggemma-2)（テキスト・画像・動画・音声を共通の 768 次元空間に写すモデル）の
**画像とテキスト**を C で実装した、写真管理向けのベースプログラムです。実行時に Python は不要で、元の `model.safetensors`（bf16）を直接読みます。

汎用部品（GEMM、RoPE、注意、safetensors、RMSNorm など）は `../catseye.h` にあり、ここにはモデル固有の部分だけがあります。

| ファイル | 内容 |
|---|---|
| `eg2e.c` | コマンド。ベクトル表示と類似検索、画像のキャッシュ。 |
| `eg2_embed.h` | 画像タワー（16 層 ViT）とテキスト本体（24 層）、前処理。 |
| `eg2_tokenizer.h` | テキストのトークナイザー（262k 語の BPE。HF と一致を確認済み）。 |
| `test_ref.c` | Python 参照出力との層ごとの照合。 |
| `tools/eg2_embed_reference.py` | 参照出力（各層）を作る。 |
| `tools/eg2_embed_tokenizer.py` | `tokenizer.json` を C 用の `.eg2t` に変換する。 |

## 使い方

```bash
make
# モデル（約 1.5 GB、ライセンスは配布元に従う）
huggingface-cli download google/embeddinggemma-2 --local-dir eg2_hf
# テキスト検索に必要なトークナイザー（1 回だけ）
python3 tools/eg2_embed_tokenizer.py eg2_hf/tokenizer.json eg2.eg2t

./eg2e -m eg2_hf vec photo.jpg                          # 768 次元の単位ベクトルを表示（-n 8 で先頭 8 個）
./eg2e -m eg2_hf sim query.jpg a.jpg b.jpg c.jpg        # 画像で似た写真を探す
./eg2e -m eg2_hf -k eg2.eg2t sim "夕焼けの海" *.jpg      # 文章で写真を探す
./eg2e -m eg2_hf -C photos.cache index *.jpg              # フォルダ全体のベクトルを先に作って保存（25 枚ごとに保存、進捗表示）
./eg2e -m eg2_hf -C photos.cache sim query.jpg *.jpg    # 保存済みの画像は即時。新しい画像だけ計算される
```

`-s` は画像 1 枚あたりのトークン数（70 / 140 / 280 / 560 / 1120、既定 140）。大きいほど細かく見えますが遅くなります。
文章は検索クエリ用のプロンプト（`task: search result | query: `）、写真の説明文など候補側の文章は文書用（`title: none | text: `）で埋め込みます。`-r` で無効にできます。

## Q4 量子化モデル（270 MB）

`quantize` で、元の `model.safetensors`（bf16）から Q4_0 版を作れます。音声タワーは含まず、テキストと画像だけを残します。

```bash
./eg2e -m eg2_hf quantize eg2_q4/model.safetensors     # 1.49 GB -> 270 MB（約 2 秒）
./eg2e -m eg2_q4 -k eg2.eg2t sim "夕焼けの海" *.jpg      # -m に量子化版のフォルダを渡すだけ
```

- 形式は GGML の Q4_0（32 要素ごとに fp16 のスケール + 4 bit）。2 次元の重み 333 個を量子化し、正規化の重みと位置テーブルは bf16 のままです。
  safetensors のヘッダーに `Q4_0` 型を持つので、他のツールでは読めません（この C 実装専用）。
- `-F` で通常の GGML のスケール（速いが誤差が約 10% 大きい）、`-K 語,語` で名前に語を含む重みを量子化せず残せます。
- 重みは mmap のままなので、起動は即時で、ピークメモリは 約 294 MB（元は 約 1.8 GB）。速度は元と同じです（140 トークンで 1 枚 約 2.9 秒）。
- 計算：トークンが 1〜3 個のときは活性化を Q8_0 にして整数内積、4 個以上は重みを展開してから float の GEMM。
  AVX のみの Xeon では後者のほうが速かったため、境界は `CATS_Q4_0_DEQUANT_MIN`（既定 4）で変えられます。

精度（fp32 の参照出力とのコサイン類似度。小さい合成データでの値）：

| 量子化の範囲 | テキスト | 画像 | サイズ |
|---|---|---|---|
| 全部 Q4（既定） | 0.992〜0.994 | 0.977〜0.987 | 270 MB |
| ビジョンを bf16（`-K vision_tower,embed_vision`） | 0.992〜0.994 | 0.987〜0.992 | 488 MB |
| テキスト本体を bf16（`-K language_model`） | 1.000 | 0.985〜0.995 | 659 MB |

検索の順位は、試した文章・画像の例では fp32 と同じでした（スコアの差は約 0.01 以内）。
写真の整理で使うなら、実際の写真で fp32 と順位を比べてから選んでください。

## 速度と精度

Xeon E5-2697 v2（12 コア、AVX のみ）での 1 枚あたり（モデル読み込みを除く）：

| 画像のトークン数 | CPU | GPU（`-G auto`、`make GPU=1`） |
|---|---|---|
| 70 | 約 1.3 秒 | — |
| 140（既定） | 約 2.7 秒 | 約 2.2 秒 |
| 280 | 約 5.8 秒 | 約 4.0 秒（`CATS_GPU_SHARE=75`） |

ピークメモリは fp32 モデルで 約 1.8 GB、Q4 で 約 0.3 GB。キャッシュ済みの画像は即時です。
12MP の JPEG のデコードは 約 0.3 秒です。`-v` で段階別の時間（注意、MLP など）を表示します。

- スレッドは物理コア数が既定です（`-j N` / `OMP_NUM_THREADS`）。ハイパースレッドの 24 スレッドにすると約 2 倍遅くなります。
- 注意は（ヘッド × 64 クエリ）の単位で並列化し、AVX で exp を 8 つずつ計算します（相対誤差 8e-8）。画像タワーの注意が 908 → 493 ms（140 トークン）になりました。
- 残りの時間の大半は行列積です。この CPU では 1 コア 約 26 GFLOPS（理論値の約 55%）で、ブロックサイズの調整では ±3% しか変わりませんでした。
  FMA/AVX2 のある CPU では、さらに速くなる余地があります（この環境では AVX2 の経路を試せていません）。
- GPU は行列積だけを担当します。結果は CPU と同じ精度でした（最終ベクトルのコサイン類似度 1.0000000）。
  テキスト本体は小さい行列が多く、重みの転送のほうが重いため、GPU 使用時は少し遅くなります。

Python（transformers, float32）の出力との照合：

- テキスト本体：全 24 層で相対誤差 約 5e-7、最終ベクトルのコサイン類似度 1.0000000。
- 画像タワー（16 層）と本体：相対誤差 約 1e-5 以下、最終ベクトルのコサイン類似度 1.0000000（前処理済みピクセルを同じにした場合）。
- 実画像（stb によるリサイズを含む）：参照とのコサイン類似度 0.9998〜0.9999。違いは前処理のリサイズだけです。

## 実際の画像での評価（ジブリ「さつき」フォルダ、518 ファイル）

`index` で全画像（`-s 140`）を fp32 と Q4 のそれぞれで処理し、`tools/eg2_eval_folder.py` で比べました。
画像は 516 枚が読み込め、残り 2 枚は拡張子が `.gif` でも中身がテキストでした（読み込み失敗は正しい動作）。1 枚 約 2.4 秒、全体で約 21 分です。

- 日本語・英語の 20 クエリ（「トトロ」「雨の中のバス停」「a girl holding an umbrella」「猫のバス」など）で、上位の画像は目視で内容に合っていました。
  fp32・Q4 の両方で、日本語の「トトロ」が『となりのトトロ』の文字入り画像にも当たりました。
- Q4 は fp32 と**順位が完全には一致しません**：画像→画像の上位 10 件の重なりは 0.80、1 位の一致は 74%（相関 0.978）。
  ただし差の大半は、ほぼ同点の候補（フォルダには重複に近い画像が多い）の入れ替えです。
  Q4 の 1 位が fp32 の最良から類似度 0.02 以内に収まる割合は 99.2%（平均の差 0.0015）、fp32 の上位 5 件が Q4 の上位 10 件に入る割合は 0.94 でした。
- 一部を高精度のまま残した版（先頭 120 枚で比較）：

| 構成 | サイズ | 1 位が 0.02 以内 | fp32 上位 5 件が Q4 上位 10 件に入る割合 |
|---|---|---|---|
| 全部 Q4 | 270 MB | 98.3% | 0.963 |
| 画像タワーを bf16 | 488 MB | 100% | 0.985 |
| テキスト本体を bf16 | 659 MB | 98.3% | 0.972 |

写真の整理・検索の用途なら、全部 Q4 で実用的です。順位の細かい違いが気になる場合は `-K vision_tower,embed_vision` が効率的です。
重複に近い画像の検出（コサイン 0.97 以上）は、fp32 で 68 組、Q4 で 61 組見つかり、Q4 のぶんはすべて fp32 にも含まれました。

## 制限

- 動画と音声は未対応です（音声タワーは `../transcript` にあります）。
- テキスト中の特殊トークン文字列（`<bos>` など）は特殊トークンとして扱いません。
- テキストのトークナイザーと画像の参照照合は、日本語・英語・絵文字などの短い文で確認しています。非常に長い文章（数千トークン）は未検証です。
- 精度は元のモデルの品質に依存します。写真検索としての良し悪しは実際の写真での評価が必要です。
